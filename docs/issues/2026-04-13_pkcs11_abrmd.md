# 问题与知识点记录 — 2026-04-13

## 问题 1：tpm2_ptool addtoken 内部爆发 `out of memory (0x902)`，手动 flush 无效

**现象**：
执行 `tpm2_ptool addtoken` 时，底层 Python 调用的 `tpm2_create` 报错 `0x902`。
即使在命令**之前**执行了完整的三连 `tpm2_flushcontext -t/-l/-s` 大扫除，依然无济于事。

**分析与原因**：
这是本次课设最具含金量的发现之一。

`tpm2_ptool addtoken` 在底层单条命令的执行周期内，会连续发起以下操作：
1. `tpm2_createprimary` — 创建主密钥（占 1 个瞬态插槽）
2. `tpm2_create` — 创建子密钥用于密封 PIN（占 1 个插槽）
3. `tpm2_sign` — 对刚创建的密钥进行 PSS 签名验证（需要加载密钥 + 开启 Hash Pipeline，再占 1~2 个插槽）

三步连招在**工具内部**就已经把仅有的 3 个瞬态内存插槽全部耗尽了。
由于这些插槽的占用发生在 Python 脚本的同一个进程内部，外部用户根本来不及插入 `tpm2_flushcontext` 进行清理。

**核心结论**：
> 当高级工具的**单条命令内部**并发 TPM 操作超过 3 个插槽时，手动 flush 彻底失效。
> 此时必须引入 **资源管理器 (TPM Resource Manager)**，由它在后台毫秒级地进行上下文的"虚拟内存换页"调度。

**解决方案**：
安装并启动 `tpm2-abrmd`（TPM Access Broker and Resource Manager Daemon）：
```bash
sudo apt install -y tpm2-abrmd libtss2-tcti-tabrmd0 libtss2-tcti-tabrmd-dev
dbus-run-session bash
tpm2-abrmd --tcti="swtpm:host=localhost,port=2321" --session &
export TPM2TOOLS_TCTI="tabrmd:bus_type=session"
export TPM2_PKCS11_TCTI="tabrmd:bus_type=session"
```

## 问题 2：TCTI 加载失败 `Could not load tcti, got: "tabrmd:bus_type=session"`

**现象**：
设置好 `TPM2_PKCS11_TCTI="tabrmd:bus_type=session"` 后执行 `tpm2_ptool init`，报错无法实例化 TCTI。

**分析与原因**：
仅安装 `tpm2-abrmd` 主程序是不够的。`tpm2-tools` 底层通过动态链接库 `.so` 来加载不同的 TCTI 驱动模块。
如果系统中没有安装 `libtss2-tcti-tabrmd0`（包含 `libtss2-tcti-tabrmd.so`），工具就找不到能够与 `tpm2-abrmd` 通信的驱动层。

此外，`tpm2-abrmd` 需要通过 D-Bus 总线与客户端通信。如果不在 `dbus-run-session bash` 开启的子终端中运行，D-Bus 会话总线不存在，资源管理器也无法被发现。

**解决方案**：
1. 安装完整的 TCTI 驱动包：`sudo apt install -y libtss2-tcti-tabrmd0 libtss2-tcti-tabrmd-dev`
2. 必须在 `dbus-run-session bash` 子终端中操作
3. 在子终端中先启动 `tpm2-abrmd --session &`，再执行后续命令

## 问题 3：PKCS#11 模块路径错误 `cannot open shared object file`

**现象**：
执行 `pkcs11-tool --module /usr/lib/x86_64-linux-gnu/libtpm2_pkcs11.so` 报错找不到文件。

**分析与原因**：
Ubuntu 22.04 的 `libtpm2-pkcs11-1` 包并不会把 `.so` 文件直接放在 `/usr/lib/x86_64-linux-gnu/` 下，
而是在更深一级的子目录 `/usr/lib/x86_64-linux-gnu/pkcs11/` 中。

使用 `find /usr/lib -name "libtpm2_pkcs11.so"` 可以快速定位到真实路径。

**解决方案**：
将路径修正为 `/usr/lib/x86_64-linux-gnu/pkcs11/libtpm2_pkcs11.so`。
文档和脚本中已全局统一修正。

## 知识点回顾：为什么实验 1-3 可以直连 swtpm，而实验 4 必须经资源管理器？

| 场景 | TPM 操作复杂度 | 单命令最大插槽占用 | 能否直连 swtpm |
|------|---------------|-------------------|---------------|
| tpm2_pcrread | 极低 | 0-1 | ✅ |
| tpm2_create + tpm2_load | 中等 | 2-3（需手动 flush） | ⚠️ 勉强 |
| tpm2_ptool addtoken | 极高 (内部并发) | >3（无法手动 flush） | ❌ 必须 abrmd |

在真实的企业级 Linux 发行版中（如 RHEL、Ubuntu Server），`tpm2-abrmd` 是开机就默认启动的系统服务。
我们在实验中用模拟器裸连的方式其实是"地狱模式"，反而帮助我们从底层深刻理解了资源管理器存在的必要性。
