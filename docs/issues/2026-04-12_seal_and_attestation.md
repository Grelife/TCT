# 问题与知识点记录 — 2026-04-12

## 问题 1：密封时报错 `structure is the wrong size (0x1D5)`

**现象**：
在执行 `tpm2_create -i test_files/secret.txt ...` 进行数据密封时报错，提示参数结构大小不对。

**分析与原因**：
TPM 并非硬盘，其内部资源特别是 NVRAM 容量极其昂贵。规范通常限制直接传入和密封的 Sensitive Data（机密数据）上限为 128 字节。之前生成的带有中文字符和冗长密码的文件超出了此限制，被 TPM 硬件直接拒收。

**知识点拓展（信封加密）**：
在真实的整盘加密（如 BitLocker 或 LUKS）中，我们并不会把几十 GB 的数据塞给 TPM。而是由操作系统生成一把 32 字节（256位）的 AES 强随机对称密钥用于加密硬盘，然后**仅把这 32 字节的 AES 密钥交给 TPM 去密封**。

**解决方案**：
替换文件内容为较短的文本即可：`echo "MySecretKey-123456" > test_files/secret.txt`。

## 问题 2：频繁遭遇 `out of memory for object contexts (0x902)`

**现象**：
在执行 `tpm2_load`、`tpm2_readpublic` 等命令时报错，内存不足。即使刚刚手动清理了终端，重新执行依然卡在此处。

**分析与原因**：
这是本次实验最重要的架构级体验。
1. **硬件局限**：真实的 TPM 芯片中的瞬态内存（Transient Memory）通常只有 **3个插槽**。复杂的高级命令（比如 Load 操作需要同时挂载“父密钥 Context”、“即将被加载的对象 Context”、“加密通信会话 HMAC Session”）会瞬间瞬间打满这3个槽。
2. **ESAPI 的漏勺局限**：在没有 **资源管理器 (TPM Resource Manager, TRM)** 帮忙自动换页和 Swap 的情况下（因为我们采用的是裸连模拟器 `-T swtpm:` 的直连形式），如果某条命令因为（例如上面超长文件）报错而闪退，底层的密码学 API 往往会“死机遗忘”清理残存在那 3 个坑位里的废弃对象。导致后续命令即使只需要 2 个槽，也再无容身之地。

**解决方案**：
我们必须充当“人工资源管理器”，通过习惯在每个加载级命令前加上 `tpm2_flushcontext -t`，强制冲刷所有的幽灵瞬态句柄，确保有干净的环境运行新命令。
- 文档中已在 `tpm2_load`、`tpm2_readpublic` 和 `tpm2_quote` 前主动加上了冲刷缓存的处理机制。

## 问题 3：Nonce 参数格式不支持 `Neither a file path nor hex string`

**现象**：
在进行远程证明时，`tpm2_quote -q 0x${NONCE}` 报错说传入的 Nonce 参数不是有效的文件路径也不是十六进制字符串。

**分析与原因**：
这是 `tpm2-tools` 底层解析器特性的一个坑。工具在接受 `-q` 等十六进制参数时，对前缀很敏感，不能加 `0x`，否则解析器会将其视作乱码或者错误的文件路径名。

**解决方案**：
去掉 `0x` 前缀，直接使用 `tpm2_quote -q ${NONCE}` 即可成功签署。文档中已全局做去除 0x 的修改。

## 知识点回顾：通过报错见证机制的生效 (a policy check failed)

在最后测试 `tpm2_unseal` 以及模拟黑客重放验证 `tpm2_checkquote` 时，分别报错：
- *a policy check failed* (解封失败)：由于此前通过脚本在 PCR 16 中写入了 `MALWARE` 字符串的哈希，污染了 PCR，TPM 果断因为状态偏离了当初打上的“封条规范”而拒绝解封密钥。
- *Error validating nonce from quote* (验证签名失败)：远程服务器发送的 Nonce 是旧的/假冒的，签名验证机制成功拦截住了“重放攻击”。

两次看似吓人的红字 ERROR 正是证明系统发挥了完美的防御作用。
